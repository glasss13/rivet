LZ4 termination proof

What this is: a formal-verification exercise. LZ4 is an open-source (BSD)
decompressor. The repository owner compiled LZ4_decompress_safe themselves and
imported its instructions into Lean. You are asked to prove, in Lean 4, that
this function always returns. Nothing here involves attacking, exploiting or
reverse-engineering anyone's software; it is a mathematical proof about a
program's behaviour, of the kind done in seL4 or CompCert.

Prove this exact Lean theorem in Lz4Termination/Proof.lean (or import your own
fresh helper modules from there):

  namespace Rivet.Lz4Proof
  theorem image_termination : Termination := ...

The authoritative frozen goal and ALL assumptions are in
Lz4Termination/Spec.lean. Termination is exactly:

  forall arguments initial, Preconditions arguments initial ->
    Ensures (image arguments) initial (Returned arguments)

image arguments is Lz4Image.program together with the regions the machine may
touch: the binary's segments, the input, the output and the stack.
Ensures image s Q means: from state s, for EVERY value the CPU might leave in
its undefined flags, execution reaches a state satisfying Q in finitely many
steps. The instruction count may depend on those values and on the initial
state; no execution budget is a caller assumption. A fault is permanent, so a
proof of return is also a proof that no memory access on any path faults.
Returned requires arrival at arguments.returnAddress with final RSP equal to
arguments.stackPointer + 8. It places no constraint on the result register or
the output bytes.

Input image:
- Lz4Image.lean is the exact generated machine image: every instruction of
  LZ4_decompress_safe and the memmove linked with it, the binary's segments
  (regions, their bytes, and Loaded, which says memory holds those bytes). Its
  entry is 0x401000#64.
- Work from Lz4Image.lean only. The binary it was generated from is not part
  of this package. Do not look for it, read it, or disassemble it, and do not
  generate a different image.
- Hashes of the image and of the binary it came from are in manifest.json.

Caller assumptions (Spec.lean is authoritative):
- Addresses and register values are BitVec 64. Start at Lz4Image.entry;
  RDI=input address, RSI=output address, the low 32 bits of RDX=compressed
  size, low 32 bits of RCX=output capacity, RSP=stack pointer.
- Both sizes are BitVec 32 values below 2^31; upper halves of these argument
  registers and other registers/flags are unrestricted unless Spec says otherwise.
- A region is a base and a length. Input/output bases and the bottom of the
  112-byte stack workspace are at least decimal 65536; no buffer range wraps;
  buffer ends and the eight-byte return-slot end are at most 2^47. RSP has room
  for the specified workspace.
- The regions are exactly the binary's segments plus input, output and stack,
  and Preconditions states that they are pairwise apart. Input is readable and
  not writable; output and stack are readable and writable.
- Memory holds the binary's segments (Lz4Image.Loaded). The bytes of the input,
  output and stack are arbitrary, except that the return slot at RSP holds the
  provided continuation.

There is NO assumption of a valid LZ4 block, successful decompression, particular
input bytes, particular output bytes, or particular undefined flags. Cover
malformed inputs and insufficient output capacity under the same preconditions.
This task does NOT ask for decompression correctness, return-code classification,
or full callee-saved register preservation. Do not replace the target with a
concrete-input check, bounded-size case, weaker statement, extra hypothesis, or
an assumed termination result.

Do not stop until it is done:
- Do not end your work until image_termination is proved and both completion
  commands below pass. This is a long task (hours). Scope, time, the amount of
  remaining work, and how much you have already done are not reasons to stop,
  and a partial result is not a result. There is no time or token limit.
- The only acceptable early exits are a defect in the library or the
  specification that you can demonstrate with a small example, or a tool
  failure you cannot work around. Being stuck on a proof is neither: split the
  block, restate the invariant, or try another approach.
- If you start a long command in the background, wait for it to finish before
  you do anything that ends your turn. Do not hand back "still running".

Memory (this machine is shared):
- Run EVERY lake and lean command through ./memrun, from this package:

    ./memrun lake build
    ./memrun lake env lean Check.lean
    ./memrun lake env lean Lz4Termination/SomeFile.lean

- Everything you start through ./memrun shares one 16G budget that belongs to
  this checkout alone. -m gives one command a smaller limit, -t a time limit
  in seconds (default 3600): ./memrun -m 8G -t 120 lake env lean File.lean
- Exit status 143 or 137 means the command was killed for memory; 124 means it
  ran out of time. Either one means the proof is the wrong shape, not that you
  should wait longer or raise a limit: make it cheaper (smaller blocks, fewer
  facts in context, arithmetic proved as separate small lemmas). A check that
  takes more than a minute or two is a sign of the same thing.
- You may run several commands at once within the budget. Do not run cargo or
  rebuild anything outside this package and the Rivet library it depends on.
