# Rivet

A Lean library for reasoning about a restricted x86-64 execution model. Programs retain instruction operands, widths, byte addresses, encoding lengths, and resolved branch targets. Lean is the only required toolchain; its version is pinned in `lean-toolchain`.

The optional [binary importer](crates/rivet-import/README.md) uses Rust and iced-x86 to generate a Lean program from all defined function symbols in a linked ELF executable. It supports Rivet's scalar and SSE instruction forms, direct calls, and returns, and emits initial bytes and permissions for ELF loadable segments; generated modules require only Lean to use.

```sh
lake build
```

`import Rivet` provides the whole library. `Rivet.Model` defines the public `MachineState` and execution functions; `Rivet.Contracts` defines uncounted block/function contracts (`Ensures`) and their composition rules. `Rivet.Instructions` provides instruction contracts proved against that interpreter, including `InstructionAt`. The API also exposes fault absorption, monotone read histories, and preservation of registers untouched by a program. `Rivet.ExecutionProperties` provides generic register-preservation and read-history properties. `Rivet.Memory` supplies `MemoryRegion` and validated `Memory` layouts. A `MachineState` requires a `Memory`; byte contents and permissions cannot be supplied as independent state fields. General-purpose registers have type `BitVec 64`; XMM registers have type `BitVec 128`. Register widths are guaranteed by construction.

The interpreter and contracts use the same state record. Access registers with `state.registers .rax`, natural-number values with `(state.registers .rax).toNat`, memory with `state.memory address`, and execution status with `state.status`. `state.memory.readable address` and `state.memory.writable address` are queries derived from the memory regions, not independently writable fields. Status is `.running address` or `.fault`; there is no observation wrapper or separate proof-state representation.

Proof contracts separate possible reachability from guaranteed eventual results:

- `Reaches program initial final` means some finite number of interpreter steps reaches `final`. It includes zero steps and allows any choice supply: `∃ choices steps, execute program steps initial choices = final`. This is possible reachability, not a guarantee that every execution reaches that state.
- `Ensures program precondition postcondition` means every state satisfying the precondition eventually reaches a state satisfying the postcondition **for every supply of undefined flag values**. This is a block contract: its postcondition can describe an intermediate instruction. `Ensures.refl` permits zero steps; it establishes no successful return by itself.

Instruction rules such as `bitwise_xor`, `read_byte`, and `return_` produce `Ensures` contracts describing the resulting state. Compose them with `first.seq second` and adapt predicates with `contract.consequence`; neither operation exposes instruction counts. `contract.run initial assumption` yields `∃ final, Reaches program initial final ∧ postcondition final`. It extracts one possible result from a contract that guarantees the postcondition for every choice supply. The universally quantified execution witness and constructor are private; `run` cannot be used in reverse to establish a universal contract from one successful execution. Function postconditions specify the caller's continuation address, restored stack pointer, and result; returning is ordinary control flow, not a terminal machine state.

The general `add` rule covers every supported scalar width and operand form. Its postcondition describes the complete result through the shared operand read/write operations, including partial-register updates, flags, fallthrough, and read history. Register/register callers can use `simpa using add program pc (.reg64 dst) (.reg64 src) state`; width is inferred, and existing location/code hypotheses or concrete checked proofs discharge instruction evidence. Symbolic immediates require encoding bounds; a memory source requires `rightReadable`, and a memory destination requires `leftReadable` and `writable` range proofs. Concrete operands normalize through constructor equations rather than unfolding unknown operands. Register-parent mappings are ordinary definitions with no global simp rules; use `simpa [Reg32.parent] using ...` when a concrete 32-bit operand must match a postcondition written with its 64-bit parent. Width conversions are transparent abbreviations: these concrete-form calls need neither width-unfolding lists nor `+instances`. For memory forms, `simpa [addressValue] using ...` can use a caller-supplied address equality. Import `Rivet.Instructions` directly for instruction contracts, or continue to use `import Rivet` for the full library.

The scalar binary rules are `add`, `sub`, `sbb`, `compare` (CMP), `test`, `bitwise_and`, `bitwise_or`, and `bitwise_xor`. Each is parametric in width and valid operand forms and states the complete successful state transition. CMP and TEST only read: even a memory destination requires no write permission. SBB uses the initial carry flag as its incoming borrow. The generalized `compare` takes operands, for example `compare program pc (.reg64 left) (.reg64 right) state`.

Control-flow rules are `nop program pc state`, `jump program pc target state`, and `branch program pc condition target state`. The general `branch` rule covers every modeled condition and changes only the program counter: it chooses `target` when `condition.holds state` is true, otherwise `program.nextAddress pc`. Concrete conditions reduce to their flag expressions when applying the rule; for example, `exact branch program pc .equal target state` also proves a goal written with `state.zeroFlag`. The former `branch_zero`, `branch_nonzero`, and `branch_below` rules are replaced by `branch` with `.equal`, `.notEqual`, and `.below`, respectively. All three rules preserve registers, flags, memory, and read history, and require no memory-access premises or instruction evidence at the destination.

Use `Ensures.intro` to build a contract by proving a block contract for each initial state satisfying the precondition. `contract.with_reachability` retains the relation between a fixed initial state and the final state alongside the postcondition; it lets `consequence` derive facts such as register preservation without opening execution witnesses. To prove a new instruction rule directly, `Ensures.of_step` requires its postcondition after one `step` for every candidate flag value. It handles the choice stream and instruction-count witness internally.

`Ensures.loop invariant finished measure body` iterates blocks until `finished` holds. For each invariant state where it does not hold, `body` must establish another invariant state with a strictly smaller natural-valued measure. Measures can describe algorithmic progress, such as bytes remaining. Ordinary induction over such a measure also composes directly with the instruction rules.

`Reaches.reads_mono`, `Reaches.not_fault`, and `Reaches.preserves_register` derive properties of execution prefixes that lead to a proved result. A non-faulted result rules out faults along that execution prefix because faults are absorbing. Reaching a continuation does not establish safety of subsequent caller execution. The former `Returns`, `Returns.to_return`, and `Returns.never_faults` APIs are removed rather than retaining their terminal-return assumptions.

`execute program steps initial choices` remains available for low-level bounded execution. `FlagChoices` is `Nat → FlagValues`, providing candidate SF/ZF bits by execution step, not instruction address. `step program state undefinedFlags` and `stepOp operation nextAddress state undefinedFlags` take one set of candidates. Instruction semantics use candidates only for undefined outputs; defined flags are calculated and preserved flags retain their previous values. Choices stay outside `MachineState`. Low-level `choices.drop count` describes the unused suffix; `execute_add` uses it to describe split execution. Block-contract composition advances the supply internally, including across loops, instead of restarting it. Stream-splicing operations and their supporting lemmas are private. Choice arguments in low-level execution/preservation theorems are implicit and inferred from the execution being discussed; only executable calls need explicit candidates. No default choice supply is implicit in the API.

IMUL consumes the SF/ZF candidates on successful execution. Other currently supported instructions define or preserve the modeled flags and ignore the candidates. The native differential validator supplies the flags observed after each native instruction and compares the complete resulting state. Proof contracts require correctness for all supplies, not merely the values observed on one CPU.

Import a function from a linked ELF executable:

```sh
cargo run -p rivet-import -- ./example --function answer --namespace Answer --output Answer.lean
```

Then import the generated module in a proof:

```lean
import Answer
open Rivet

-- Answer.entry is the function's byte address; Answer.program contains its decoded instructions.
```

The importer supplies addresses, instruction lengths, operands, branch targets, and `regions : List Rivet.MemoryRegion` from the binary. Construct memory from `Answer.regions` plus regions for the stack and buffers using `Memory.ofRegions`; it returns an error for overlapping or out-of-bounds layouts. Put the resulting `Memory` into the initial `MachineState`. There is no overlay initialization or fallback memory: unmapped addresses have no permissions. Regions support symbolic contents through an offset-indexed byte function; imported contents use a `ByteArray` with an implicit zero-filled tail. This models ELF-declared byte ranges, not exact Linux page mappings or process startup. Regenerate the module when the binary changes. Lean checks proofs about the generated program; correspondence to the binary depends on the importer and iced-x86. You can also construct `Program` values directly using Rivet's instruction types. Lean does not parse assembly text.

`readBytes memory address size` decodes little-endian bytes into `BitVec (8 * size)` for scalar, vector, and return-address reads. `Memory.storeBytes` is the common byte-range update; `MachineState.writeMemory` updates only the memory field. These raw operations do not check permissions. Instructions check `permits` for the complete access before changing state; `permits_iff` exposes its address bound and per-byte permissions. Stores preserve permissions and bytes outside their range. `Memory.read_storeBytes` describes the updated value at a mapped address without requiring write permission. The former `read64`, `readMemory`, and byte-store wrappers are removed. For example, a zero-extended byte read is `(readBytes memory address 1).setWidth 64`, and a return-address value is `(readBytes memory address 8).toNat`.

Each `Instruction` contains `address`, `length`, and `op`. `Program` remains a list, but list positions no longer control execution. `Program.fetch` finds an instruction at an exact byte address, accepting only 64-bit addresses and lengths from 1 to 15. Missing addresses, including undeclared addresses in the middle of an instruction, fault when fetched. Ordinary execution advances to `(address + length) % 2^64`; branches use byte addresses. `Program.nextAddress` exposes that fallthrough for contracts; callers should establish `InstructionAt` at that address first. Lookup uses the first matching valid entry.

`AtInstruction state address`, `InstructionAt program address operation`, and the instruction rules refer to byte addresses. `Ensures` contracts do not expose instruction counts. The importer resolves RIP-relative operands to absolute addresses; imported regions supply the initial data and permissions for those references. Proofs still supply registers, stack, and input/output buffers. Direct CALL pushes the next instruction's address and jumps to its target; plain RET pops an address and continues there. Neither terminates execution. Missing instructions fault when fetched. A function proof establishes eventual arrival at its caller's continuation with the required state, without instruction counts or special stop addresses in the model. ELF parsing and instruction decoding remain outside Lean; instruction fetch uses the supplied decoded program rather than executable memory.

`mov` supports 8/16/32/64-bit registers, integer immediates, and sized memory operands. Addresses support a base, an optional index scaled by 1/2/4/8, and an integer displacement, for example `mov eax, DWORD PTR [rdi + 8*rcx - 4]`. Byte and word register writes preserve the remaining bits; 32-bit writes clear the upper half. Memory-to-memory moves, mismatched widths, and unencodable immediates are rejected. A 64-bit memory destination accepts a signed 32-bit immediate, as required by its encoding.

`movups` and `movdqu` support the legacy 128-bit memory↔XMM moves used by LZ4, for example `movups xmm0, XMMWORD PTR [rsi]` and `movdqu XMMWORD PTR [rdi + 16], xmm0`. Both copy all 128 bits without interpretation, allow unaligned addresses, and preserve flags and general-purpose registers. Loads require read permission for all sixteen bytes and record a sixteen-byte read; stores require only write permission. A failed check faults before changing registers or memory. XMM0–XMM15 are accessible through `state.xmmRegisters`; the field defaults to zero when omitted from a state literal. Structured instructions use `.loadXmm .movups .xmm0 address` and `.storeXmm .movdqu address .xmm0`. Register-to-register MOVUPS/MOVDQU forms are not yet supported. These semantics assume SSE/SSE2 is enabled and alignment checking is disabled, following Intel's [MOVDQU](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=657) and [MOVUPS](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=718) specifications.

`movd xmm, r32` copies the low 32 bits of a general-purpose register into an XMM register and zeroes its upper 96 bits. `pshufd xmm, xmm, imm8` selects each of four destination dwords from the original source, using successive two-bit fields of the immediate (0–255), starting with the lowest destination dword. Source and destination may be the same register. Both preserve flags, general-purpose registers, memory, and read history. Structured forms are `.movd .xmm0 .edx` and `.pshufd .xmm0 .xmm0 0`; the latter repeats the source's lowest dword four times. Only these register forms are supported, without memory operands, reverse MOVD, MMX, or AVX. See [Intel's instruction specification](https://cdrdv2-public.intel.com/825757/253667-sdm-vol-2b.pdf).

`lea r64, [address]` computes an address without reading memory or checking access permissions. `movzx r32, source` zero-extends a byte or word register/memory source; `movsxd r64, source` sign-extends a dword register/memory source. All three preserve flags. Extension loads check the full memory range and record its original effective address.

`add`, `sub`, `sbb`, `cmp`, `test`, `and`, `or`, and `xor` support 8/16/32/64-bit register, immediate, and memory operands. Widths must match, at most one operand may be memory, and 64-bit forms accept only signed 32-bit immediates. TEST requires its memory operand, if any, first. SBB subtracts the source and incoming CF, reporting unsigned borrow in CF. CMP and TEST update flags without writing their operands. Arithmetic and logic memory destinations require read and write permission; CMP and TEST require only read permission.

`imul destination, source` and `imul destination, source, immediate` support 16/32/64-bit register destinations and matching register or memory sources. The two-operand form multiplies the old destination by the source; the three-operand form multiplies the source by the immediate. The low product bits are written with the usual partial-register rules. CF reports whether the signed product fits the destination width; undefined SF and ZF come from the step's candidate bits. Memory sources require only read permission and are recorded; faults leave registers and flags unchanged. 64-bit immediates must fit signed 32 bits. One-operand IMUL and 8-bit forms are not supported. OF, which has the same overflow meaning as CF here, remains outside the model. These semantics follow [Intel's IMUL specification](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=494).

`shl register, count` and `shr register, count` support only the forms needed by LZ4: 32/64-bit register destinations and immediate counts from 0 to 255 (including the count-one encoding). Counts are masked to five or six bits respectively. Nonzero shifts compute CF from the last bit shifted out and SF/ZF from the result. A zero effective count preserves flags; a 32-bit destination still clears its parent register's upper half. These supported widths never produce undefined CF after count masking. Memory destinations, 8/16-bit operands, CL counts and SAR are not supported. See [Intel's shift specification](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366721.pdf#page=281). The structured form is `.shift .shl (.reg32 .edx) 16` (or `.shr`).

`not` complements an 8/16/32/64-bit register or memory operand and preserves flags. A memory destination requires both read and write permission.

`jmp` branches to a byte address. `jcc`, `setcc`, and `cmovcc` share the conditions E/Z (equal), NE/NZ (not equal), B (below), AE (above or equal), BE (below or equal), A (above), and S (sign), written as ordinary mnemonics such as `ja`, `sete`, and `cmovne`. SETcc writes 0 or 1 to a byte register or byte memory operand. CMOVcc accepts a 16/32/64-bit register destination and a matching register or memory source. Its memory source is read and checked even when the condition is false; a 32-bit destination clears its upper 32 bits in either case. All these instructions preserve flags.

`push r64` stores the original register value at RSP−8 and updates RSP. `pop r64` reads at the old RSP, increments RSP, then writes the destination; POP RSP therefore leaves the loaded value in RSP. Both preserve flags and check the full eight-byte access before changing state. PUSH requires write permission; POP requires read permission and records the read. They use ordinary memory without changing permissions or erasing popped bytes. Immediate, memory-operand, and 16-bit PUSH/POP forms are not yet supported.

The model also supports 64-bit register `inc` and `dec`, and `ret`. All sixteen general-purpose registers and their 32-bit, 16-bit, and low-byte aliases are available; high-byte aliases are not supported. See the [importer documentation](crates/rivet-import/README.md) for accepted binary encodings and current limitations.

Structured MOV operations use `Operand` for their source and destination, for example `.mov (.reg32 .eax) (.immediate 42)`. `Address` describes the effective address, and `Width` describes memory operand sizes. The `move` contract covers these forms with source-read and destination-write permission hypotheses. Truncating multiplication uses `.imul destination source immediate`, where `immediate` is `none` for register/memory multiplication or `some value` for the immediate form. Scalar operations use `.binary`, for example `.binary .add (.reg32 .eax) (.immediate 1)`. Conditional instructions use the same `Condition` type: `.jcc .above 12`, `.setcc .sign (.reg8 .al)`, or `.cmovcc .notEqual (.reg32 .eax) (.reg32 .edx)`.

Proofs concern the shared model. Decoder and processor correspondence remain assumptions; the translation from machine code is not formally verified. ZF, CF, and SF are modeled. Arithmetic and logic compute flags at the operand width; INC and DEC preserve CF. Overflow, parity, and auxiliary carry flags are not yet modeled. Memory has separate `readable` and `writable` permissions; multi-byte accesses check the entire range before changing state, and MOV stores do not require read permission. Effective-address arithmetic wraps at 64 bits; accesses spanning the address-space boundary fault. Executions have no concurrency or asynchronous interference.

A developer-only [differential validation harness](crates/rivet-check/README.md) compares the interpreter with native x86-64 execution. Its Rust and Linux tooling requirements are separate from library use.

Rust tools share a Cargo workspace under `crates/`, with one root lockfile and build directory. Run `cargo run -p rivet-import -- ...` for the importer, `cargo run -p rivet-check -- ...` for validation, or `cargo clippy --workspace -- -D warnings` to check both packages.
