# Rivet

A Lean library for reasoning about a restricted x86-64 execution model. Programs retain instruction operands, widths, byte addresses, encoding lengths, and resolved branch targets. Lean is the only required toolchain; its version is pinned in `lean-toolchain`.

The optional [binary importer](crates/rivet-import/README.md) uses Rust and iced-x86 to generate a Lean program from all defined function symbols in a linked ELF executable. It supports Rivet's scalar and SSE instruction forms, direct calls, and returns, and emits initial bytes and permissions for ELF loadable segments; generated modules require only Lean to use.

```sh
lake build
```

`import Rivet` provides the whole library. `Rivet.Model` defines the public `MachineState` and execution functions; `Rivet.Contracts` defines uncounted block/function contracts (`Ensures`) and their composition rules. `Rivet.Instructions` provides instruction contracts proved against that interpreter. `InstructionAt program address length operation` states that `program.fetch address = some ⟨address, length, operation⟩`; `rivet_fetch` (in `Rivet.Fetch`) proves it. `Rivet.Contracts` provides fault absorption, monotone read histories, preservation of registers untouched by a program, and memory preservation through `Reaches`; their execution proofs are private. `Rivet.Contracts` also provides the stopped-execution law `execute_stopped`. `Rivet.Step` provides the `rivet_step` tactic for executing a block one instruction at a time. `Rivet.Memory` supplies the flat `Memory` (a byte and read/write permissions at every address) and `MemoryRegion` layouts for building one. A `MachineState` requires a `Memory`. General-purpose registers have type `BitVec 64`; XMM registers have type `BitVec 128`. Register widths are guaranteed by construction.

For any `reached : Reaches program initial final`, `reached.preserves_readable` and `reached.preserves_writable` show that execution preserves both permission maps. `reached.preserves_unwritable address readonly` preserves the byte at `address`, given `readonly : initial.memory.writable address = false`. These guarantees cover every finite execution, including faulting executions, without assumptions about the program or undefined flag choices. They protect read-only and unmapped bytes; writable bytes may change.

The interpreter and contracts use the same state record. Access registers with `state.registers .rax`, memory with `state.memory address`, and execution status with `state.status`. Addresses are `BitVec 64` throughout: memory, permissions, instruction addresses, jump and call targets, the program counter and read history, so effective addresses computed from registers index memory directly. Status is `.running address` or `.fault`; there is no observation wrapper or separate proof-state representation.

Proof contracts separate possible reachability from guaranteed eventual results:

- `Reaches program initial final` means some finite number of interpreter steps reaches `final`. It includes zero steps and allows any choice supply: `∃ choices steps, execute program steps initial choices = final`. This is possible reachability, not a guarantee that every execution reaches that state.
- `Ensures program precondition postcondition` means every state satisfying the precondition eventually reaches a state satisfying the postcondition **for every supply of undefined flag values**. This is a block contract: its postcondition can describe an intermediate instruction. `Ensures.refl` permits zero steps; it establishes no successful return by itself.

Instruction rules such as `bitwise_xor`, `movzx`, and `return_` produce `Ensures` contracts describing the resulting state. Compose them with `first.seq second` and adapt predicates with `contract.consequence`; neither operation exposes instruction counts. `contract.run initial assumption` yields `∃ final, Reaches program initial final ∧ postcondition final`. It extracts one possible result from a contract that guarantees the postcondition for every choice supply. The universally quantified execution witness and constructor are private; `run` cannot be used in reverse to establish a universal contract from one successful execution. Function postconditions specify the caller's continuation address, restored stack pointer, and result; returning is ordinary control flow, not a terminal machine state.

The general `add` rule covers every supported scalar width and operand form. Its postcondition describes the complete result through the shared operand read/write operations, including partial-register updates, flags, fallthrough, and read history. Register/register callers can use `simpa using add program pc (.reg64 dst) (.reg64 src) state`; width is inferred, and existing location/code hypotheses or concrete checked proofs discharge instruction evidence. Symbolic immediates require encoding bounds; a memory source requires `rightReadable`, and a memory destination requires `leftReadable` and `writable` range proofs. Concrete operands normalize through constructor equations rather than unfolding unknown operands. Register-parent mappings are ordinary definitions with no global simp rules; use `simpa [Reg32.parent] using ...` when a concrete 32-bit operand must match a postcondition written with its 64-bit parent. Width conversions are transparent abbreviations: these concrete-form calls need neither width-unfolding lists nor `+instances`. For memory forms, `simpa [addressValue] using ...` can use a caller-supplied address equality. Import `Rivet.Instructions` directly for instruction contracts, or continue to use `import Rivet` for the full library.

The scalar binary rules are `add`, `sub`, `sbb`, `compare` (CMP), `test`, `bitwise_and`, `bitwise_or`, and `bitwise_xor`. Each is parametric in width and valid operand forms and states the complete successful state transition. CMP and TEST only read: even a memory destination requires no write permission. SBB uses the initial carry flag as its incoming borrow. The generalized `compare` takes operands, for example `compare program pc (.reg64 left) (.reg64 right) state`.

SIMD rules are `movd`, `pshufd`, `load_xmm`, and `store_xmm`. MOVD copies a GPR's low 32 bits and zeroes the destination XMM register's upper 96 bits. PSHUFD accepts any encoded byte control, selecting each output dword from the initial source with a two-bit selector; lane 0 is least significant, and source/destination aliasing is supported. Its postcondition uses bitvector lane extraction and concatenation. XMM loads/stores share one rule per direction parameterized by `XmmMove` (MOVUPS or MOVDQU), require only the corresponding 16-byte read/write permission, and impose no alignment premise. Loads append a read-history entry; stores serialize little-endian bytes and preserve history. All four rules preserve flags and GPRs, and modify only their stated XMM or memory destination.

The `imul program pc destination source immediate state` rule covers the modeled 16/32/64-bit two-operand (`none`) and immediate-multiplier (`some value`) forms, with matching register or memory sources. It specifies the truncated signed product, carry flag for signed overflow, fallthrough, and read history. SF/ZF are existential Boolean values in the postcondition: they are unconstrained while the contract still holds for every undefined-flag supply. No flag-supply types are exposed by the rule. Width and routine validity are inferred; memory sources require read permission, and symbolic immediates require the appropriate encoding bounds. A caller can unpack `⟨sign, zero, equal⟩` and use the known effects without assigning arithmetic meaning to those flags.

The `shift program pc operation destination count state` rule covers the modeled immediate-count SHL/SHR forms: 32-bit and 64-bit register destinations with an encoded count below 256. Width is inferred from the destination, and the effective count is reduced modulo 32 or 64. A zero effective count preserves flags while still writing the destination, so an r32 shift clears the upper half even then. Nonzero counts update carry from the last shifted-out bit, zero from the result, and sign from its most significant bit. Memory, read history, and other registers are preserved; no memory-access premises are needed.

The `bitwise_not`, `setcc`, and `cmovcc` rules preserve flags. NOT covers supported register and memory destinations, requiring read/write permission for memory. SETcc is condition-parametric and writes a byte without a memory-read premise. CMOVcc is condition-parametric across supported 16/32/64-bit register destinations and matching register or memory sources. Its memory source must be readable even when the condition is false; the access is recorded on either path. An untaken 32-bit CMOVcc still clears the upper half of its parent register. Concrete forms infer validity and discharge irrelevant access premises automatically.

Address and extension rules are `lea`, `movzx`, and `movsxd`. LEA evaluates any modeled effective address without memory-access premises. MOVZX covers byte/word register and memory sources into a 32-bit destination; MOVSXD covers dword register and memory sources into a 64-bit destination. Both preserve flags and require read permission only for memory sources. Their complete postconditions use the initial source value and address, including when source and destination alias. Use `movzx program pc destination (.memory .byte address) state` in place of the former specialized `read_byte` rule; register sources discharge their access and width premises automatically.

Control-flow rules are `nop program pc state`, `jump program pc target state`, and `branch program pc condition target state`. The general `branch` rule covers every modeled condition and changes only the program counter: it chooses `target` when `condition.holds state` is true, otherwise the fall-through address `pc + length`. Concrete conditions reduce to their flag expressions when applying the rule; for example, `exact branch program pc .equal target state` also proves a goal written with `state.zeroFlag`. The former `branch_zero`, `branch_nonzero`, and `branch_below` rules are replaced by `branch` with `.equal`, `.notEqual`, and `.below`, respectively. All three rules preserve registers, flags, memory, and read history, and require no memory-access premises or instruction evidence at the destination.

Stack rules are `push program pc source state` and `pop program pc destination state`, covering the modeled 64-bit register forms. PUSH requires write permission for `[rsp - 8, rsp)`; POP requires read permission for `[rsp, rsp + 8)`. PUSH RSP stores the original pointer. POP increments RSP before writing its destination, so POP RSP replaces that incremented value with the loaded word. PUSH preserves read history; POP records its eight-byte read. Both preserve flags, with POP preserving memory as well. Location, instruction evidence, and matching permission hypotheses can be inferred from context.

Use `Ensures.intro` to build a contract by proving a block contract for each initial state satisfying the precondition. `contract.with_reachability` retains the relation between a fixed initial state and the final state alongside the postcondition; it lets `consequence` derive facts such as register preservation without opening execution witnesses. The single-step bridge used to prove instruction contracts is private.

`first.bind continuation` continues from each state satisfying `first`'s postcondition, given as a variable. For an exact-state contract `Ensures program (· = s) (· = e)`, the continuation receives a fresh state `t` and `t = e` instead of the expression `e`, so successive steps do not nest record updates.

`rivet_step` applies the contract of the instruction at the current address of an `Ensures program (· = s) Q` goal, given a hypothesis `s.status = .running pc`, where `pc` is an address literal or an expression that reduces to one, such as an imported `entry` or `entry + 3#64`. It continues from a fresh successor with one fact per field (`t.registers = …`, `t.memory = …`, `t.status = .running next`, and so on), simplified through operand reads and writes. Effective addresses become register reads, such as `s.registers .rbx - 8#64`, rather than expressions over the whole register file. An unnamed successor is inaccessible, and its facts refer to the state before it, so each step costs the same however long the block. `rivet_step as t` names the successor as a checkpoint: its facts, path conditions, and your hypotheses are rewritten in terms of the previous named state in one pass, and the unnamed states in between are cleared. Name states where you want readable facts, such as loop heads. Path conditions at a conditional jump are always stated in terms of named states. Facts are inaccessible; use them with `simp [*]` (preferable to `simp_all` between checkpoints), or retrieve one by statement, such as `‹t.memory = _›`. The location and instruction evidence are supplied directly. Other side conditions that `rfl`, `decide`, `assumption`, and then `simp [*]` cannot prove remain as goals tagged with the contract's parameter name, such as `case writable`; `rivet_step (disch := tac)` replaces the `simp [*]` fallback. A conditional jump produces goals tagged `taken` and `fallthrough`, each with its path condition stated in terms of flags. `rivet_step tracking [status, registers, memory]` records only the listed fields; facts that would depend on an untracked field are dropped. IMUL's unconstrained SF/ZF become fresh variables. A store appears as `memory.storeBytes a (a + 8#64) (littleEndianAt value a)`. Word literals in facts are in `simp`'s normal form, `0x1003#64`; compare statuses with `simp` rather than a bare `rw`.

```lean
example (s : MachineState) (h : s.status = .running 0x1000) :
    Ensures prog (· = s) (fun f => f.registers .rcx = s.registers .rax + s.registers .rbx + 1) := by
  rivet_step                      -- mov rcx, rax
  rivet_step                      -- add rcx, rbx
  rivet_step                      -- inc rcx
  exact Ensures.refl.consequence (fun _ h => h) (fun _ e => by subst e; simp_all [BitVec.add_assoc])
```

The tactic only applies existing contracts and composition laws; Lean checks every step.

Proving which instruction is at an address means following `Program.fetch`, a first-match search of the instruction list, so a direct proof costs time proportional to the instruction's position. Generated programs avoid this by construction. `program.FetchesFrom suffix address` states that at and above `address`, `program` fetches as `suffix` does. The importer emits `program` as a chain of suffixes, `program.suffix_<a>` being the program from the instruction at address `a` on, with one fact per instruction, `program.from_<a> : program.FetchesFrom program.suffix_<a> a`. Each fact follows from the previous one by `FetchesFrom.skip`, which passes over one lower-addressed instruction, so the chain takes linear time to check once. `rivet_step` uses `program.from_<pc>` when it exists, so looking up an instruction and proving its `InstructionAt` fact take time independent of the program size. For other programs it searches the list.

`Ensures.loop invariant finished measure body` iterates blocks until `finished` holds. For each invariant state where it does not hold, `body` must establish another invariant state with a strictly smaller natural-valued measure. Measures can describe algorithmic progress, such as bytes remaining. Ordinary induction over such a measure also composes directly with the instruction rules.

`Reaches.reads_mono`, `Reaches.not_fault`, and `Reaches.preserves_register` derive properties of execution prefixes that lead to a proved result. A non-faulted result rules out faults along that execution prefix because faults are absorbing. Reaching a continuation does not establish safety of subsequent caller execution. The former `Returns`, `Returns.to_return`, and `Returns.never_faults` APIs are removed rather than retaining their terminal-return assumptions.

Every instruction rule takes the instruction as `code : InstructionAt program pc length operation`, with `length` implicit, and states its successor as `pc + BitVec.ofNat 64 length`, which reduces to an address literal. The default proof of `code` is `rivet_fetch`, which fills in `length` from the program: in time independent of the program size for generated programs, by searching the list for other concrete programs, and from a hypothesis for abstract programs. The location defaults to `rfl` or a hypothesis. Concrete programs normally need neither argument; abstract programs can supply these facts as hypotheses without unfolding the interpreter.

`execute program steps initial choices` remains available for low-level bounded execution. `FlagChoices` is `Nat → FlagValues`, providing candidate SF/ZF bits by execution step, not instruction address. `step program state undefinedFlags` takes one set of candidates. Its implementation and opcode helpers are hidden from ordinary module imports; instruction contracts provide the proof interface. Instruction semantics use candidates only for undefined outputs; defined flags are calculated and preserved flags retain their previous values. Choices stay outside `MachineState`. Low-level `choices.drop count` describes the unused suffix; `execute_add` uses it to describe split execution. Block-contract composition advances the supply internally, including across loops, instead of restarting it. Stream-splicing operations and their supporting lemmas are private. Choice arguments in low-level execution/preservation theorems are implicit and inferred from the execution being discussed; only executable calls need explicit candidates. No default choice supply is implicit in the API.

IMUL consumes the SF/ZF candidates on successful execution. Other currently supported instructions define or preserve the modeled flags and ignore the candidates. The native differential validator supplies the flags observed after each native instruction and compares the complete resulting state. Proof contracts require correctness for all supplies, not merely the values observed on one CPU.

Import a function from a linked ELF executable:

```sh
cargo run -p rivet-import -- ./example --function answer --namespace Answer --output Answer.lean
```

Then import the generated module in a proof:

```lean
import Answer
open Rivet

-- Answer.entry is the function's byte address; Answer.program contains its decoded instructions.
```

The importer supplies addresses, instruction lengths, operands, branch targets, and `regions : List Rivet.MemoryRegion` from the binary. Construct memory from `Answer.regions` plus regions for the stack and buffers using `Memory.ofRegions`, and put it into the initial `MachineState`. Addresses outside every region have no permissions and read zero. A byte in overlapping regions comes from the first; proofs about contents assume `regions.Pairwise MemoryRegion.Disjoint`. A region is `{ start, stop, contents, readable, writable }` covering `[start, stop)`, with `contents` giving the byte at each absolute address, concrete or symbolic; imported contents use a `ByteArray` with an implicit zero-filled tail. This models ELF-declared byte ranges, not exact Linux page mappings or process startup. Regenerate the module when the binary changes. Lean checks proofs about the generated program; correspondence to the binary depends on the importer and iced-x86. You can also construct `Program` values directly using Rivet's instruction types. Lean does not parse assembly text.

`readBytes memory address size` decodes `size` little-endian bytes from `address` into `BitVec (8 * size)` for scalar, vector, and return-address reads. A `Memory` has three fields, `bytes`, `readable` and `writable`, each indexed by address; `memory address` is `memory.bytes address`. A memory range is a pair of addresses `[start, stop)`, compared unsigned, so a range with `start ≤ stop` does not wrap. `memory.storeBytes start stop bytes` gives every address in the range its byte from `bytes`; scalar stores (`MachineState.writeMemory`) and XMM stores both write `littleEndianAt value address`, byte `i` of the value at `address + i`. These raw operations do not check permissions. Instructions check `permits permission start stop` for the complete access before changing state; `permits_iff` states it as `start ≤ stop` plus permission at every address in the range, and `permits_valid` extracts `start ≤ stop`. Stores preserve permissions (`Memory.readable_storeBytes`, `Memory.writable_storeBytes`), `Memory.read_storeBytes` gives each byte after a store, and `Memory.read_storeBytes_outside` a byte outside it. For example, a zero-extended byte read is `(readBytes memory address 1).setWidth 64`, and a return address is `readBytes memory rsp 8`.

Memory lemmas state ranges as word comparisons, so their side conditions close by `bv_omega`. A read of `size` bytes from `address` covers `[address, address + size)`; lemmas about it also ask that the read not wrap, `address ≤ address + size`, which its permission provides through `permits_valid`, and that `size < 2^64`.

- `Memory.readBytes_storeBytes_within` reads inside a store; `readBytes_littleEndianAt` and `readBytes_littleEndianAt_add` turn a read of a stored value into `value.extractLsb' …`. A load after a store usually closes by `simp (disch := bv_omega) [*, Memory.readBytes_storeBytes_within]`.
- `Memory.readBytes_storeBytes_disjoint` reads outside a store.
- `permits_within` narrows a permission to a subrange.
- `before.SameOutside after footprint` says that memory changed only inside `footprint : BitVec 64 → Prop`, a set of addresses such as `fun a => out ≤ a ∧ a < outEnd`. It has `refl`, `trans`, `mono` (enlarge the footprint), and `storeBytes` (a store inside the footprint). Its frame law is `agree.readBytes`: a read outside the footprint is unchanged. `Reaches.preserves_unwritable` states that execution changes memory only where it was writable.
- For `Memory.ofRegions regions`, `Memory.permits_readable_ofRegions` and `Memory.permits_writable_ofRegions` give a region's permission over the whole region. Given `regions.Pairwise MemoryRegion.Disjoint`, `Memory.read_ofRegions`, `Memory.readable_ofRegions` and `Memory.writable_ofRegions` give exactly the byte and permissions at an address inside a region (so read-only data is unwritable), and `Memory.readBytes_ofRegions` reads a range of its contents. Each takes the region's membership and reads its fields from it, so state the region when proving membership: `have input : ({ start := base, stop := limit, contents := bytes, readable := true, writable := false } : MemoryRegion) ∈ regions := by simp [regions]`. `simp [regions, MemoryRegion.Disjoint] at disjoint` turns the disjointness hypothesis into word comparisons for `bv_omega`.

Each `Instruction` contains `address`, `length`, and `op`. `Program` remains a list, but list positions no longer control execution. `Program.fetch` finds an instruction at an exact `BitVec 64` address, accepting only lengths from 1 to 15. Missing addresses, including undeclared addresses in the middle of an instruction, fault when fetched. Ordinary execution advances to `address + length`, wrapping like any word; branches use byte addresses. Contracts state that fall-through directly from the instruction's `length`. Lookup uses the first matching valid entry.

`state.status = .running address`, `InstructionAt program address length operation`, and the instruction rules refer to byte addresses. `Ensures` contracts do not expose instruction counts. The importer resolves RIP-relative operands to absolute addresses; imported regions supply the initial data and permissions for those references. Proofs still supply registers, stack, and input/output buffers. Direct CALL pushes the next instruction's address and jumps to its target; plain RET pops an address and continues there. Neither terminates execution. Missing instructions fault when fetched. A function proof establishes eventual arrival at its caller's continuation with the required state, without instruction counts or special stop addresses in the model. ELF parsing and instruction decoding remain outside Lean; instruction fetch uses the supplied decoded program rather than executable memory.

`mov` supports 8/16/32/64-bit registers, integer immediates, and sized memory operands. Addresses support a base, an optional index scaled by 1/2/4/8, and an integer displacement, for example `mov eax, DWORD PTR [rdi + 8*rcx - 4]`. Byte and word register writes preserve the remaining bits; 32-bit writes clear the upper half. Memory-to-memory moves, mismatched widths, and unencodable immediates are rejected. A 64-bit memory destination accepts a signed 32-bit immediate, as required by its encoding.

`movups` and `movdqu` support the legacy 128-bit memory↔XMM moves used by LZ4, for example `movups xmm0, XMMWORD PTR [rsi]` and `movdqu XMMWORD PTR [rdi + 16], xmm0`. Both copy all 128 bits without interpretation, allow unaligned addresses, and preserve flags and general-purpose registers. Loads require read permission for all sixteen bytes and record a sixteen-byte read; stores require only write permission. A failed check faults before changing registers or memory. XMM0–XMM15 are accessible through `state.xmmRegisters`; the field defaults to zero when omitted from a state literal. Structured instructions use `.loadXmm .movups .xmm0 address` and `.storeXmm .movdqu address .xmm0`. Register-to-register MOVUPS/MOVDQU forms are not yet supported. These semantics assume SSE/SSE2 is enabled and alignment checking is disabled, following Intel's [MOVDQU](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=657) and [MOVUPS](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=718) specifications.

`movd xmm, r32` copies the low 32 bits of a general-purpose register into an XMM register and zeroes its upper 96 bits. `pshufd xmm, xmm, imm8` selects each of four destination dwords from the original source, using successive two-bit fields of the immediate (0–255), starting with the lowest destination dword. Source and destination may be the same register. Both preserve flags, general-purpose registers, memory, and read history. Structured forms are `.movd .xmm0 .edx` and `.pshufd .xmm0 .xmm0 0`; the latter repeats the source's lowest dword four times. Only these register forms are supported, without memory operands, reverse MOVD, MMX, or AVX. See [Intel's instruction specification](https://cdrdv2-public.intel.com/825757/253667-sdm-vol-2b.pdf).

`lea r64, [address]` computes an address without reading memory or checking access permissions. `movzx r32, source` zero-extends a byte or word register/memory source; `movsxd r64, source` sign-extends a dword register/memory source. All three preserve flags. Extension loads check the full memory range and record its original effective address.

`add`, `sub`, `sbb`, `cmp`, `test`, `and`, `or`, and `xor` support 8/16/32/64-bit register, immediate, and memory operands. Widths must match, at most one operand may be memory, and 64-bit forms accept only signed 32-bit immediates. TEST requires its memory operand, if any, first. SBB subtracts the source and incoming CF, reporting unsigned borrow in CF. CMP and TEST update flags without writing their operands. Arithmetic and logic memory destinations require read and write permission; CMP and TEST require only read permission.

`imul destination, source` and `imul destination, source, immediate` support 16/32/64-bit register destinations and matching register or memory sources. The two-operand form multiplies the old destination by the source; the three-operand form multiplies the source by the immediate. The low product bits are written with the usual partial-register rules. CF reports whether the signed product fits the destination width; undefined SF and ZF come from the step's candidate bits. Memory sources require only read permission and are recorded; faults leave registers and flags unchanged. 64-bit immediates must fit signed 32 bits. One-operand IMUL and 8-bit forms are not supported. OF, which has the same overflow meaning as CF here, remains outside the model. These semantics follow [Intel's IMUL specification](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=494).

`shl register, count` and `shr register, count` support only the forms needed by LZ4: 32/64-bit register destinations and immediate counts from 0 to 255 (including the count-one encoding). Counts are masked to five or six bits respectively. Nonzero shifts compute CF from the last bit shifted out and SF/ZF from the result. A zero effective count preserves flags; a 32-bit destination still clears its parent register's upper half. These supported widths never produce undefined CF after count masking. Memory destinations, 8/16-bit operands, CL counts and SAR are not supported. See [Intel's shift specification](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366721.pdf#page=281). The structured form is `.shift .shl (.reg32 .edx) 16` (or `.shr`).

`not` complements an 8/16/32/64-bit register or memory operand and preserves flags. A memory destination requires both read and write permission.

`jmp` branches to a byte address. `jcc`, `setcc`, and `cmovcc` share the conditions E/Z (equal), NE/NZ (not equal), B (below), AE (above or equal), BE (below or equal), A (above), and S (sign), written as ordinary mnemonics such as `ja`, `sete`, and `cmovne`. SETcc writes 0 or 1 to a byte register or byte memory operand. CMOVcc accepts a 16/32/64-bit register destination and a matching register or memory source. Its memory source is read and checked even when the condition is false; a 32-bit destination clears its upper 32 bits in either case. All these instructions preserve flags.

`push r64` stores the original register value at RSP−8 and updates RSP. `pop r64` reads at the old RSP, increments RSP, then writes the destination; POP RSP therefore leaves the loaded value in RSP. Both preserve flags and check the full eight-byte access before changing state. PUSH requires write permission; POP requires read permission and records the read. They use ordinary memory without changing permissions or erasing popped bytes. Immediate, memory-operand, and 16-bit PUSH/POP forms are not yet supported.

The model also supports 64-bit register `inc` and `dec`, and `ret`. All sixteen general-purpose registers and their 32-bit, 16-bit, and low-byte aliases are available; high-byte aliases are not supported. See the [importer documentation](crates/rivet-import/README.md) for accepted binary encodings and current limitations.

Structured MOV operations use `Operand` for their source and destination, for example `.mov (.reg32 .eax) (.immediate 42)`. `Address` describes the effective address, and `Width` describes memory operand sizes. The `move` contract covers these forms with source-read and destination-write permission hypotheses. Truncating multiplication uses `.imul destination source immediate`, where `immediate` is `none` for register/memory multiplication or `some value` for the immediate form. Scalar operations use `.binary`, for example `.binary .add (.reg32 .eax) (.immediate 1)`. Conditional instructions use the same `Condition` type: `.jcc .above 12`, `.setcc .sign (.reg8 .al)`, or `.cmovcc .notEqual (.reg32 .eax) (.reg32 .edx)`.

Proofs concern the shared model. Decoder and processor correspondence remain assumptions; the translation from machine code is not formally verified. ZF, CF, and SF are modeled. Arithmetic and logic compute flags at the operand width; INC and DEC preserve CF. Overflow, parity, and auxiliary carry flags are not yet modeled. Memory has separate `readable` and `writable` permissions; multi-byte accesses check the entire range before changing state, and MOV stores do not require read permission. Effective-address arithmetic wraps at 64 bits; accesses spanning the address-space boundary fault. Executions have no concurrency or asynchronous interference.

A developer-only [differential validation harness](crates/rivet-check/README.md) compares the interpreter with native x86-64 execution. Its Rust and Linux tooling requirements are separate from library use.

Rust tools share a Cargo workspace under `crates/`, with one root lockfile and build directory. Run `cargo run -p rivet-import -- ...` for the importer, `cargo run -p rivet-check -- ...` for validation, or `cargo clippy --workspace -- -D warnings` to check both packages.
