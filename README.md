# Rivet

A Lean library for reasoning about restricted Intel-syntax x86-64 assembly. Programs retain instruction operands, widths, source lines, and resolved branch targets. Lean is the only required toolchain; its version is pinned in `lean-toolchain`.

```sh
lake build
```

`import Rivet` provides the whole library. `Rivet.Model` defines the public `MachineState` and execution functions; `Rivet.Contracts` defines uncounted block contracts (`Ensures`), successful function contracts (`Returns`), and instruction rules proved against that interpreter. The API also exposes fault absorption, monotone read histories, and preservation of registers untouched by a program. `Rivet.Parser` defines the accepted source grammar. `Rivet.ExecutionProperties` provides generic register-preservation and read-history properties. Registers have type `BitVec 64`, so register width is guaranteed by construction.

The interpreter and contracts use the same state record. Access registers with `state.registers .rax`, natural-number values with `(state.registers .rax).toNat`, memory with `state.memory address`, and execution status with `state.status`. Status is `.running instructionIndex`, `.returned address`, or `.fault`; there is no observation wrapper or separate proof-state representation.

Proof contracts separate reachability, successful return, and ongoing safety:

- `Reaches program initial final` means some finite number of interpreter steps reaches `final`. It includes zero steps and allows any choice supply: `∃ choices steps, execute program steps initial choices = final`. This is possible reachability, not a guarantee that every execution reaches that state.
- `Ensures program precondition postcondition` means every state satisfying the precondition eventually reaches a state satisfying the postcondition **for every supply of undefined flag values**. This is a block contract: its postcondition can describe an intermediate instruction. `Ensures.refl` permits zero steps; it establishes no successful return by itself.
- `Returns program precondition postcondition` additionally requires the final status to be `.returned address` for some address. Use `contract.returns` with a proof that the block's postcondition implies return. A postcondition already true initially cannot establish `Returns` from a running or faulted state without reaching a successful return.
- `Always program initial property` states that the property holds at every finitely reachable state, including the initial state. `Always.induction` proves this from an initial fact and preservation by `step` for every candidate flag value.
- `Diverges program initial` means every finite prefix under every choice supply remains running. `Diverges.of_progress` accepts an invariant whose states are running and, after taking one instruction with any candidate flags, satisfy an `Ensures` contract reaching another invariant state. This guarantees positive progress without a step-count witness. Zero-step reachability and stopped-state stuttering cannot establish divergence.

Instruction rules such as `clear`, `read_byte`, and `return_` produce `Ensures` contracts describing the resulting state. Compose them with `first.seq second` and adapt predicates with `contract.consequence`; neither operation exposes instruction counts. `contract.run initial assumption` yields `∃ final, Reaches program initial final ∧ postcondition final`. It extracts one possible result from a contract that guarantees the postcondition for every choice supply. The universally quantified execution witness and constructor are private; `run` cannot be used in reverse to establish a universal contract from one successful execution. For a `Returns` contract, the postcondition also contains the successful-return fact.

Use `Ensures.intro` to build a contract by proving a block contract for each initial state satisfying the precondition. `contract.with_reachability` retains the relation between a fixed initial state and the final state alongside the postcondition; it lets `consequence` derive facts such as register preservation without opening execution witnesses. To prove a new instruction rule directly, `Ensures.of_step` requires its postcondition after one `step` for every candidate flag value. It handles the choice stream and instruction-count witness internally.

`Ensures.loop invariant finished measure body` iterates blocks until `finished` holds. For each invariant state where it does not hold, `body` must establish another invariant state with a strictly smaller natural-valued measure. Measures can describe algorithmic progress, such as bytes remaining. Ordinary induction over such a measure also composes directly with the instruction rules.

`Returns.to_return` uses a universal return contract to show that every reachable state has a successful continuation satisfying the postcondition. Final states can differ between choice supplies; arbitrary reachable states are not assumed to lie on one deterministic path. Together with `Reaches.reads_mono`, `Reaches.not_fault`, and `Reaches.preserves_register`, this supports safety proofs for all execution prefixes without calculating a return budget. `contract.never_faults initially` derives fault freedom directly from a `Returns` contract and its precondition.

`execute program steps initial choices` remains available for low-level bounded execution. `FlagChoices` is `Nat → FlagValues`, providing candidate SF/ZF/CF bits by execution step, not instruction address. `step program state undefinedFlags` and `stepOp operation state undefinedFlags` take one set of candidates. Instruction semantics use candidates only for undefined outputs; defined flags are calculated and preserved flags retain their previous values. Choices stay outside `MachineState`. Low-level `choices.drop count` describes the unused suffix; `execute_add` and `execute_execute` use it to describe split execution. Block-contract composition advances the supply internally, including across loops, instead of restarting it. Stream-splicing operations and their supporting lemmas are private. Choice arguments in low-level execution/preservation theorems are implicit and inferred from the execution being discussed; only executable calls need explicit candidates. No default choice supply is implicit in the API.

IMUL consumes the SF/ZF candidates on successful execution. Other currently supported instructions define or preserve the modeled flags and ignore the candidates. The native differential validator supplies the flags observed after each native instruction and compares the complete resulting state. Proof contracts require correctness for all supplies, not merely the values observed on one CPU.

Define a program directly from assembly in your proof module:

```lean
import Rivet
open Rivet

def source : String := include_str "input.s"
def program : Program := assembly% source
```

`include_str` embeds the file contents at elaboration time, relative to the Lean source file. `assembly%` runs the existing parser and stores its resulting instructions with a kernel-checked proof that they equal the parsed source. Invalid assembly is an elaboration error. Later proofs use the stored program without evaluating the parser again. There is no generated instruction-list file or separate parser implementation, and no native-evaluation axiom is required. Recompile the containing Lean module after changing its assembly input. `parse` remains available for runtime parsing.

`mov` supports 8/16/32/64-bit registers, integer immediates, and sized memory operands. Addresses support a base, an optional index scaled by 1/2/4/8, and a signed 32-bit displacement, for example `mov eax, DWORD PTR [rdi + 8*rcx - 4]`. Decimal literals without leading zeroes and hexadecimal literals are accepted; `movabs r64, immediate` is also supported. Byte and word register writes preserve the remaining bits; 32-bit writes clear the upper half. Memory-to-memory moves, mismatched widths, and unencodable immediates are rejected. A 64-bit memory destination accepts a signed 32-bit immediate, as required by its encoding.

`lea r64, [address]` computes an address without reading memory or checking access permissions. `movzx r32, source` zero-extends a byte or word register/memory source; `movsxd r64, source` sign-extends a dword register/memory source. All three preserve flags. Extension loads check the full memory range and record its original effective address.

`add`, `sub`, `sbb`, `cmp`, `test`, `and`, `or`, and `xor` support 8/16/32/64-bit register, immediate, and memory operands. Widths must match, at most one operand may be memory, and 64-bit forms accept only signed 32-bit immediates. TEST requires its memory operand, if any, first. SBB subtracts the source and incoming CF, reporting unsigned borrow in CF. CMP and TEST update flags without writing their operands. Arithmetic and logic memory destinations require read and write permission; CMP and TEST require only read permission.

`imul destination, source` and `imul destination, source, immediate` support 16/32/64-bit register destinations and matching register or memory sources. The two-operand form multiplies the old destination by the source; the three-operand form multiplies the source by the immediate. `imul register, immediate` is normalized to the three-operand form with that register as its source. The low product bits are written with the usual partial-register rules. CF reports whether the signed product fits the destination width; undefined SF and ZF come from the step's candidate bits. Memory sources require only read permission and are recorded; faults leave registers and flags unchanged. 64-bit immediates must fit signed 32 bits. One-operand IMUL and 8-bit forms are not supported. OF, which has the same overflow meaning as CF here, remains outside the model. These semantics follow [Intel's IMUL specification](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366621.pdf#page=494).

`not` complements an 8/16/32/64-bit register or memory operand and preserves flags. A memory destination requires both read and write permission.

`jmp` branches to a label. `jcc`, `setcc`, and `cmovcc` share the conditions E/Z (equal), NE/NZ (not equal), B (below), AE (above or equal), BE (below or equal), A (above), and S (sign), written as ordinary mnemonics such as `ja`, `sete`, and `cmovne`. SETcc writes 0 or 1 to a byte register or byte memory operand. CMOVcc accepts a 16/32/64-bit register destination and a matching register or memory source. Its memory source is read and checked even when the condition is false; a 32-bit destination clears its upper 32 bits in either case. All these instructions preserve flags.

`push r64` stores the original register value at RSP−8 and updates RSP. `pop r64` reads at the old RSP, increments RSP, then writes the destination; POP RSP therefore leaves the loaded value in RSP. Both preserve flags and check the full eight-byte access before changing state. PUSH requires write permission; POP requires read permission and records the read. They use ordinary memory without changing permissions or erasing popped bytes. Immediate, memory-operand, and 16-bit PUSH/POP forms are not yet supported.

The remaining grammar accepts 64-bit register `inc` and `dec`, and `ret`, with one initial `.globl NAME` declaration. All sixteen general-purpose registers and their 32-bit, 16-bit, and low-byte aliases are available; high-byte aliases, RIP-relative symbols, and address-size overrides are not supported. Other directives and instruction forms are rejected.

Labels occupy their own lines and may contain letters, digits, underscores, and dots, but cannot begin with a digit. Leading-dot labels such as `.LBB23_156:` are recognized before directives. The bare `.` current-location symbol and Intel expression/type keywords are forbidden as label names; keyword checks ignore case. Duplicate labels, undefined branch targets, and unsupported directives remain errors.

Structured MOV operations use `Operand` for their source and destination, for example `.mov (.reg32 .eax) (.immediate 42)`. `Address` describes the effective address, and `Width` describes memory operand sizes. The `move` contract covers these forms with source-read and destination-write permission hypotheses. Truncating multiplication uses `.imul destination source immediate`, where `immediate` is `none` for register/memory multiplication or `some value` for the immediate form. Scalar operations use `.binary`, for example `.binary .add (.reg32 .eax) (.immediate 1)`. Conditional instructions use the same `Condition` type: `.jcc .above 12`, `.setcc .sign (.reg8 .al)`, or `.cmovcc .notEqual (.reg32 .eax) (.reg32 .edx)`.

Proofs concern the shared model. Assembler and processor correspondence remain assumptions; machine code is not verified. ZF, CF, and SF are modeled. Arithmetic and logic compute flags at the operand width; INC and DEC preserve CF. Overflow, parity, and auxiliary carry flags are not yet modeled. Memory has separate `readable` and `writable` permissions; multi-byte accesses check the entire range before changing state, and MOV stores do not require read permission. Effective-address arithmetic wraps at 64 bits; accesses spanning the address-space boundary fault. Executions have no concurrency or asynchronous interference.

A developer-only [differential validation harness](validation/README.md) compares the interpreter with native x86-64 execution. Its Rust and Linux tooling requirements are separate from library use.
