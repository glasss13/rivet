# Rivet differential validation

Developer-only harness for **x86-64 Linux with glibc**. Rust compares actual CPU execution against Rivet's compiled Lean interpreter; it contains no reference implementation of the instruction semantics.

Requires the repository's Lean toolchain, stable Rust/Cargo, and permission to trace a child with `ptrace`. The root `lake build` remains Lean-only.

The bridge uses [lean-json](https://github.com/paulbutcher/lean-json) for JSON and automatic codecs; its deriving support is imported only at compile time.

From the repository root:

```sh
cargo run --locked -p rivet-check -- --cases 1000 --seed 20261105
```

This builds the Lean model and generates cases from a seeded random generator biased toward arithmetic boundaries. The harness checks individual instructions with varied operands, short branching programs, randomized matched PUSH/POP sequences, and nested direct calls with repeated calls to shared callees. Whole programs run for at most 64 instructions; loops may return, fault, or remain running at that limit. RSI, the generated countdown register, is sometimes initialized to a small value to exercise terminating loops. The generator constructs iced instructions directly and encodes them into machine-code bytes; the shared `rivet-import` library decodes those bytes at their actual mapped address into the structured instructions sent to Lean. Native execution runs those same bytes. The generator no longer supplies the model program independently. Branching programs preserve the return stack and use RDI as their data pointer; stack sequences restore the original return slot.

Encoding uses iced’s typed assembler API without assembly text, external assembler processes, or temporary object files. Iced labels resolve branch targets during generation. Saved cases contain the encoded bytes and final encoder offsets, so replay does not regenerate or re-encode the program. The generated blocks use internal branches and register-based memory addressing, so their bytes can be copied into the executable mapping without relocation.

Both runners stop at the designated harness completion address (the end of the code block), on a fault, or at the step limit. A RET inside the program continues normally. Completion is a runner convention: the final model state is still `.running stopAddress`. The low-level Lean interpreter has no completion address and does not stop on RET.

Each case is prepared once in `src/setup.rs`, producing two separate values: `ExecutionInput` is the program with byte addresses/lengths and initial-state data; `NativeMemory` owns the executable code and data/stack allocations. Native execution receives both. After native execution, Lean receives `ExecutionInput` plus the observed SF/ZF/CF values after each instruction. It does not access the native process or its resources.

The observation after native step zero supplies the candidate undefined flag bits for model step zero, and so on, including repeated loop iterations. Only Lean instruction semantics decide which flags, if any, are undefined; Rust does not duplicate that classification. Defined flags are calculated independently, preserved flags retain their old values, and the runner rejects missing or unused flag observations. IMUL consumes the SF/ZF candidates on successful execution; other supported instructions ignore them. Generated programs may immediately branch on these flags or consume them with SETcc/CMOVcc: both executions follow the behavior observed on this CPU.

After each instruction it compares all sixteen general-purpose registers, all sixteen 128-bit XMM registers, ZF, CF, SF, instruction location, running/fault status, and every byte of the controlled data/stack memory. The parent reads the stopped child’s memory through `/proc/PID/mem`, so copy-on-write pages are observed correctly. Randomly read-only data pages and accesses around an inaccessible guard page exercise store, load, CALL stack-write, and RET stack-read faults, including multi-byte accesses whose first byte is accessible. Iced’s block encoder supplies native instruction offsets after resolving labels and choosing branch encodings. The shared decoder resolves branch targets and instruction lengths from the bytes. Both traces report the actual RIP; the model advances by the decoded instruction length. Native boundary checks use encoder offsets rather than decoder output. Encoding and decoding now share iced, so this path no longer provides an independent assembler cross-check.

Multi-instruction programs start RSP on a controlled stack. Individual PUSH/POP cases place the accessed slot in data or near the guard page to exercise unaligned accesses, read-only memory, and faults. All sixteen registers, including RSP itself, are generated. IMUL generation covers two/three-operand forms, 16/32/64-bit destinations, signed immediates, register/memory sources, and following flag consumers without definedness restrictions. SHL/SHR generation is limited to immediate counts and 32/64-bit registers, with uniformly random byte counts. MOVUPS/MOVDQU generate 128-bit memory loads/stores with any XMM register and uniformly random initial XMM bits. MOVD covers any 32-bit general-purpose source and XMM destination; PSHUFD covers arbitrary XMM sources/destinations and uniformly random byte immediates. Native XMM state is initialized and read through the Linux floating-point register set. SBB exercises both incoming carry values; NOT checks flag preservation. MOV and scalar arithmetic/logic generation cover register, immediate, load, and store forms at 8/16/32/64 bits, including partial-register writes, scaled indices, signed displacements, and unaligned accesses. MOVZX covers byte/word register and memory sources; MOVSXD covers dword register and memory sources. SETcc covers byte register and memory destinations; CMOVcc covers 16/32/64-bit registers and memory sources. All seven supported conditions are generated for jumps, SETcc, and CMOVcc, with random initial flags. Unconditional jumps also exercise loops. The comparison includes false-condition CMOV loads, access faults, and 32-bit destination zero-extension. LEA uses the same address expressions without memory access, including arbitrary register values that can produce wrapped or noncanonical addresses. Load/store base registers are initialized near controlled data or the guard boundary; index registers receive small offsets (or a mapped address for index-only operands). Replay recreates these bindings so it works across different ASLR addresses.

A mismatch prints the seed, case number, and case JSON. The `code` field is an array of instruction bytes; `offsets` records encoder instruction boundaries and the end of the block. Register-value arrays retain the same order as Lean's `registerOrder`. `xmmRegisters` contains sixteen arrays of four unsigned 32-bit words, lowest word first, in XMM0–XMM15 order. The replay format replaces the old structured `program` field; old operation-list cases must be regenerated. Save the case JSON to rerun it:

```sh
cargo run --locked -p rivet-check -- --replay /tmp/case.json
```

Exit codes: **0** = passed; **1** = semantic mismatch; **2** = infrastructure, protocol, or invalid-input error.

The native runner forks a traced child per case and single-steps it with a two-second stop deadline. Each model invocation has a five-second deadline, including pipe I/O. Both processes are cleaned up on errors.

This is bounded observational testing of the choices observed on the host CPU, not exhaustive exploration of all allowed choices. Library contracts quantify over all choice supplies. It checks ZF, CF, and SF rather than all RFLAGS, compares generic fault status, and does not observe memory-read events or memory outside the controlled pages. Reaching the instruction budget compares an execution prefix; it does not prove termination.
